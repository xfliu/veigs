4.3 Notes on the comparison

  • MATLAB startup cost (loading INTLAB, JIT-warming veigs, etc.) is excluded — only steady-state runs are timed.

  • Sparse path: not exercised here. MATLAB veigs uses Arpack eigs for sparse approximate eigenvalues; Julia currently always uses dense eigen. For n ≤ 100 (the README problem regime) the dense path is faster anyway.

v1 (initial implementation): Cost dominated by interval-matmul of the reconstruction L*D*Lᵀ in verified_ldl and R'·R in verified_isspd — both O(n³) generic-loop interval ops with no BLAS path.

v2 — first algorithmic insight (2026-05-01): the algorithm contract does not require an interval LDL or interval R'R. An approximate (float) reconstruction plus a Wilkinson-style backward-error bound is sufficient — the downstream verified_isspd PD check (which is itself the post-processing step that absorbs slack) closes the soundness loop. Float gemm + scalar γ_n·‖L‖²·‖D‖ bound, but the σ_min(R) sub-problem still used interval back-substitution against unit vectors — that's where the remaining cost lived.

v3 — second algorithmic insight (2026-05-01): R⁻¹ never appears in the verified-eigenvalue algorithm — the outer driver verifies PD-ness by trying a candidate ρ and checking that M − ρI is PD via LDL+inertia. verified_isspd can use the same shift trick on itself: pick a small ρ, compute verified_ldl(M − ρI), read the inertia of D, and bound the residual operator norm. If ‖E‖₂ < ρ, Weyl gives λ_min(M) ≥ ρ − ‖E‖₂ > 0. No σ_min(R), no interval back-sub. The interval-LDL residual itself was retightened to a per-entry Wilkinson bound γ_{3n}·(|L|·|D|·|Lᵀ|)_{ij} (two extra BLAS gemms of positive matrices) — required because on the banded n=10 example, ‖L‖_∞ ~ 1e8 blew up the scalar inf-norm bound.

v4 — adopting Rump 2006 as default (2026-05-01): After v3 landed, a literature check pointed to Rump's BIT 2006 paper "Verification of Positive Definiteness" (the same algorithm INTLAB's isspd uses). Theorem 2.3 + Corollary 2.4 + §3 eq. (I) give a single-Cholesky verified-PD test with a closed-form a-priori shift c = γ_{n+1}/(1 − γ_{n+1})·tr(|A|) + n·M·eta. Implemented alongside v3 and switched to default; v3 retained as method = :ldl_shift for cross-validation.

Result at n=1000: 113 s → 31 s → 1.03 s → 0.68 s, a cumulative 166× speedup, with bound width bit-identical (7.76e-16) across v3 and v4 and all 723 tests still passing under either method. n=5000: 64.8 s. Scaling n=1000 → n=2000 is 5× (close to expected for Cholesky); n=2000 → n=5000 is 19× (cache pressure past 2000² = 4 M doubles). At v4, the MATLAB sparse path was ~5× faster (Julia v4 64.8 s vs MATLAB ~13 s at n=5000); since v7+v8 Julia is ~30× faster than the same MATLAB harness — see §4.4.2 and §4.4.3 for the corrected (2026-05-02) baseline.

4.4.2 MATLAB veigs+INTLAB on truly sparse inputs (corrected 2026-05-02)

MATLAB veigs handles sparse inputs natively: eigs for the approximate eigensolve, sparse ldl for the factorization, INTLAB sparse intval matmul for the residual. Bandwidth-1 (tridiagonal) inputs admit O(n) sparse LDL with no fill-in.

Phase-9 correction (2026-05-02). The previously reported MATLAB baselines (0.093 / 0.147 / 0.311 s for n=1000 / 2000 / 5000) were inconsistent with a fresh run on the same machine. Measured with a clean A/B harness (veigs/bench_inertia_apples.m), the picture depends on which SIGMA target is requested. The 1D Laplacian's smallest eigenvalue is positive, so for an SPD problem 'smallestabs' ('sm') and 'smallestreal' ('sa') return the same eigenvalue mathematically, but trigger different code paths inside eigs:

Why the two SIGMA targets diverge. 'smallestabs' internally tells MATLAB's eigs to use shift-invert mode with σ=0: factor (A − 0·B) = A via sparse LU, run Lanczos against x ↦ A⁻¹·(B·x). Lanczos on the inverse converges rapidly because the eigenvalues of A⁻¹ are 1/λi — the smallest λ becomes the dominant inverse eigenvalue, well-separated. 'smallestreal' instead uses plain Lanczos on the original operator; for a problem like ours where λmin ≈ 4×10⁻⁷ is poorly separated from machine zero, Lanczos fails to converge inside the default iteration cap and veigs.m:127 falls back to dense eig(full(mid(A)), full(mid(B))) on a 5000×5000.

Independent confirmation. User's interactive measurement on the same problem with tic; veigs(A,B,1,'sm'); toc; gave 0.32–0.33 s per call — about 8× our scripted bench's 0.039 s. Both confirm that 'sm' is in the sub-second regime; the 8× spread between scripted and interactive MATLAB is presumably JIT/warm-state differences. We use the scripted figure (0.039 s) for the comparison since it matches the Julia harness's protocol (5 timed reps after 2 warm-ups inside a function).

4.4.2.1 Effect of the GetInertia.m patch (2026-05-02)

The user observed that GetInertia.m calls D = intval(D) upfront, hypothesising that this materialises an n×n intval matrix and is a cheap-win. We patched GetInertia.m to extract diag(D), diag(D,1), diag(D,-1) once and operate on those vectors instead, only intval-promoting the four scalars per 2×2 block on demand. The original is preserved as GetInertia_orig.m for direct A/B.

At the per-call level (n=5000, real D from a sparse LDL, 100 reps, warmed):

variant median (ms) trim mean (ms) speedup
GetInertia_orig (baseline) 174–223 175–236 1×
GetInertia (patched) 5.7 5.7 ~30×

The patch is a real ~30× per-call win, but does not meaningfully change full-veigs wall-clock at this size: GetInertia is called once per veigs run for ~6 ms inside an 11–19 s total. INTLAB's intval(sparse) already preserves sparsity, so the original code wasn't actually allocating n² intervals; the slow part was per-element scalar indexing into a sparse intval matrix inside the loop. The diagonal-extraction patch bypasses that path. The cheap-win the user hypothesised existed algorithmically but its target was not on the wall-clock critical path.

Profiling showed inertia(D::Matrix{Float64}) was ~14 % of v7 wall time at n=5000 — entirely from interval.(D) broadcasting over a 25 M-entry matrix whose only nonzero entries are on the diagonal (D comes from SymTridiagonal LDL). v7 (2026-05-02): upstream sparsity preservation in veigs_driver. Removed the unconditional interval.(Matrix(A)) at line 95 — when the input is SparseMatrixCSC, we now use interval.(A) directly, which broadcasts over the nonzero pattern and returns SparseMatrixCSC{Interval{Float64}}. v6 (2026-05-01): tridiagonal fast path added to verified_ldl and _verified_isspd_rump2006. When the dense interval matrix has bandwidth ≤ 1, both routines extract a SymTridiagonal view of the midpoint and use ldlt(::SymTridiagonal) (stdlib, O(n)). The pentadiagonal reconstruction L·D·Lᵀ + Wilkinson bound is also computed closed-form in O(n) instead of via three dense BLAS gemms. Cuts n=5000 wall time from 40.3 s → 19.4 s — about half the residual gap to MATLAB. Bounds still ULP-tight (7.93e-16). The remaining 60× gap is in O(n²) dense interval-matrix overhead upstream of the factorisation (Ai = interval.(Matrix(A)) still densifies; sym_hull, Mi[p,p], the dense permutation copies). Closing that needs sparse interval matrices end-to-end (the proper iter-8 work).

The crossover has moved with v3. Below n ≈ 1000, Julia wins by 1–2 orders of magnitude on dense small problems; LAPACK BLAS dominates the cost and Julia's call overhead is much lower than MATLAB's. Around n=1000 the two are now within a small constant factor. Above that, MATLAB still wins because MATLAB+INTLAB keeps the LDL factorization sparse (no fill-in for tridiagonal: O(n) cost), while Julia densifies at verified_ldl entry and pays O(n²) memory + O(n³) BLAS time. Bound precision is identical: both implementations produce ~8e-16-wide bounds at all sizes, both contain λ_true. The remaining gap is structural (sparse vs dense factorization), not algorithmic.

What it would take to close the rest. Iter 8's sparse-aware verified_ldl would need three changes: (a) keep SparseMatrixCSC at entry, (b) use Cholmod's sparse LDLᵀ factorization (or a sparse Bunch-Kaufman if available), (c) compute the residual L*D*Lᵀ over a sparse interval matrix without densifying. With v3 the dense path already handles n ≈ 5000 in 90 s; the sparse-aware path would extend Julia's verified-eigenvalue range to the n=20000+ regime where MATLAB currently dominates.

4.5.1 v15 — explicit tightness/speed trade-off via outer_matmul

v14's worst-case Wilkinson bound widens by ~15× on tridiagonal-style problems with integer multipliers, where the actual rounding is often zero. Rather than choose, v15 surfaces the trade-off as a kwarg:

                                       # use :tight for v12-equivalent
mode bound width (n=5000 1D Laplacian) wall (median of 3, ms) kernel
:fast (default) 2.7e-15 3.3 float gemm + per-entry Wilkinson γ_k

Both are sound; both enclose the truth. :tight is 19× slower for 15× tighter intervals — useful when the per-entry bound matters (e.g., extreme-precision research). The public veigs(A, B, k, sigma) API is unchanged and uses the default. All 728 tests pass (5 new for the kwarg).

The :fast trick pays off dramatically more at BigFloat than at Float64. At Float64 BLAS makes the gemm hyper-optimized so the gap to interval×float is "only" ~20×; at BigFloat there is no BLAS for either path, so the speedup comes purely from avoiding per-element directed-rounding overhead. That overhead dominates as n grows:

BigFloat(256), 1D Laplacian, smallest eigenvalue. Practical implication: BigFloat verification is only feasible at scale through :fast. The Wilkinson bound at BigFloat ULP yields width ≈ 10⁻³⁰, well below any algorithmic floor (separator gaps, residual norm), so :tight's extra rounding tightness is noise at that scale. The conclusion: :fast is the right default at both precisions; :tight is a niche tool for ULP-tight Float64 on integer-multiplier sparse matrices.

4.5.2 v16 — verified_ldl dense path (mid, rad) refactor (#6)

The dense Bunch-Kaufman fallback (taken whenever the matrix is not tridiagonal — 2D Laplacians, FEM mass matrices, etc.) was the last place still doing per-entry interval arithmetic at O(N²). 4.5.3 v17 — sparse no-pivot LDL fast path (#7)

An apples-to-apples MATLAB+INTLAB bench on the 2D Laplacian P1 FEM problem revealed a 47× gap at N=3600 (Julia 6.24 s vs MATLAB 0.13 s). Diagnosis: verified_ldl fell back to dense Bunch-Kaufman on non-tridiag inputs because Julia stdlib has no sparse symmetric indefinite LDL. MATLAB+INTLAB calls MA57 from HSL.

Fix: route sparse non-tridiag inputs through LDLFactorizations.jl (pure Julia, AMD fill-reducing ordering, sparse symbolic-then-numerical LDL).   • :auto (default) — sparse first, dense fallback.
  • :dense — force dense BK (legacy / debugging).
  • :ldlfac — force sparse, error on zero pivot.
  • :mumps — documented seam for future MUMPS.jl integration (option 2). Throws with implementation guidance.

4.5.5 v19 — Dumbbell domain: clustered eigenvalues, real verification

The dumbbell domain — two unit squares connected by a thin bar of width w=0.2 — is the canonical spectral-geometry test for tight near-degenerate eigenvalues. The first two eigenvalues form a cluster near 2π² ≈ 19.74 (symmetric / antisymmetric ground state, split by tunneling through the bar). Beyond that, the (2,1)/(1,2) modes form a four-fold cluster near 5π². These are exactly the cases that veigs's cluster expansion was designed to handle correctly.

Probed behaviour at h=0.025 P1 (3 609 DOFs):

  • k=2 → returns cluster 1 with bound widths 2.4×10⁻¹¹; gap λ_2 − λ_1 = 2.05×10⁻⁴ rigorously enclosed.
  • k=3, 4, 5 → throws VeigsClusterTooLargeError. Refusing to half-count a cluster is the correct soundness behaviour.
  • k=6 → returns clusters 1+2 (6 eigenvalues), all rigorously separated, max bound width 1.3×10⁻¹⁰.

4.6 Precision option (v13) — Lehmann–Goerisch with BigFloat

v13 adds a precision::Type{<:AbstractFloat} = Float64 kwarg to lehmann_behnke. When precision !== Float64, every interval op inside the routine — including the outer n×m matmuls — runs at the requested precision, so the inner Lehmann–Goerisch step (and the final cluster bounds) carry tighter intervals than the Float64 ULP floor.

This is the policy from DESIGN.md §3: Float64 is the default; higher precision is opt-in. The kwarg is intended for problems where the user genuinely needs bounds below ~10⁻¹⁶ × |λ|, or as a diagnostic to determine whether bound widths are limited by arithmetic or by the algorithm itself.

Probe result (bench/precision_probe.jl): n=50 1D Laplacian, smallest eigenvalue, exact analytical eigenvector V passed in.

precision bound width time per call (warm) observation
Float64 1.54e-16 ~ms ~ULP floor for λ ≈ 4×10⁻³

BigFloat(512 bits) 2.47e-29 ~14 ms same as 256 bits — saturated
BigFloat(1024 bits) 2.47e-29 ~14 ms same — confirms floor

The bound-width floor at ~2.47×10⁻²⁹ across BigFloat precision-bits settings shows the floor is set by the algorithm's residual term (Err = ‖B·nV − A·V‖² / λ_B_min) and the input separator gap, not by arithmetic precision. This is the diagnostic DESIGN.md §3 specified — a useful probe for practitioners debugging ill-posed-looking eigenvalue problems.

Cost: BigFloat arithmetic is ~100× slower than Float64 in the outer matmul. The kwarg is for small problems and diagnostic use, not production sparse n=5000 work. For production, run at Float64 default and accept the ULP floor; switch to BigFloat only when (a) the user asks for tighter bounds than Float64 allows, or (b) the cluster matrix is so ill-conditioned that the inner-EVP residual swallows the gap. Reproducible script at bench/precision_probe.jl.

BottleneckWhere it bitesMitigation status
Interval matrix multiplication is generic (no BLAS) Quadratic-cubic terms in verified_isspd, verified_ldl, lehmann_behnke all use Matrix{Interval}*Matrix{Interval} which falls into a generic loop. Roughly 100× slower than float matmul of the same shape. Open. Future fix: store as mid+rad (two Float64 matrices) and form products via two BLAS calls — covered in plan §4.3 but not implemented.
Cubic scaling on veig at n > 25 n=25 takes 49 ms; n=50 takes 624 ms (~12.7×). The hard cap of n=100 was deliberately kept (Q-004) so the cluster-aware veigs driver is used for larger problems. By design. Larger problems should call veigs with a small k.
Sparse input is densified throughout the pipeline Three places force densification: (1) _approx_eig calls eigen(Symmetric(A_mid), Symmetric(B_mid)) on the full dense matrix; (2) verified_ldl calls Matrix(M) at entry because Julia's bunchkaufman is dense-only; (3) the interval residual L*D*Lᵀ is computed as a dense interval matrix product. Mitigation requires (a) sparse-aware verified_ldl using Cholmod's sparse LDL where applicable, (b) sparse interval residual via the matrix-free residual norm bound, (c) Arpack eigs(A, B; nev, sigma) for the approximate eigensolve.

7 — Merits

  • Soundness preserved end-to-end. The library was explicitly designed around the rule "a fast wrong answer has zero value" (guide.md §11). Every routine has at least one adversarial test that constructs a counter-example and asserts the conservative answer.
  • Bounds match MATLAB+INTLAB, sometimes tighter. Identical to within ~10% on the README golden examples; tighter on 4 of 5 banded-test bounds, presumably from CRlibm-correctly-rounded arithmetic in IntervalArithmetic.jl.
  • 26×–307× faster than MATLAB+INTLAB on small dense problems (matched inputs, same rounding model in spirit). The Hilbert n=8 cluster of 3 takes 0.95 ms in Julia versus 290 ms in MATLAB. The advantage flips at n ≈ 1000 sparse — see §4.4.
  • Test discipline: per-routine corner-case taxonomy embedded as a comment block at the top of every test_*.jl; seed-pinned random tests; one bench file per routine; soundness asymmetry documented (must-fail-closed vs. allowed-conservative).
  • Comprehensive coverage: 723 passing assertions across 7 routines, including a 50-matrix LDL reconstruction regression and a 9-construction soundness battery for verified_isspd.
  • Decision provenance: every non-trivial design choice is logged in DECISIONS.md with a [PENDING-CONFIRM] tag plus a per-iteration journal entry. Reviewers can audit why each routine looks the way it does.
  • Reproducibility: Manifest.toml pins every dependency; Random.seed!(20260501) at the top of every test file; the timing protocol in this report is documented and easily re-run.
