Veigs.jl — open questions on publishing

Status as of 2026-05-01. Iters 1–7 are 🟢 (723 tests passing). Iter 8 (docs + CI + sparse path) and the questions below are the remaining decision points before a public release.

Current state of the repository

  • The MATLAB tree veigs/ ships an MIT License, Copyright (c) 2025 Xuefeng Liu, Yuuka Yanagisawa.
  • The Julia tree Veigs.jl/ has no LICENSE file and is not yet a git repository.
  • Project.toml lists authors = ["Xuefeng Liu", "Yuuka Yanagisawa"] but has no license field, no repo URL.
  • Package version is 0.1.0-dev.
Why these questions matter now. Julia treats source code with no LICENSE as all rights reserved by default. Even kept private, the package needs an explicit license so you (or a co-author) can later re-distribute it cleanly. Registration is a separate, larger commitment but inherits whatever license you pick now.

Q-002 — License

Three sensible options

OptionWhat it saysWhen to pick
A. Copy MIT verbatim from veigs/LICENSE (the DECISIONS.md default) Same MIT terms; same copyright notice "2025 Xuefeng Liu, Yuuka Yanagisawa" You consider the Julia port a translation of the MATLAB toolbox under the same authorship and same terms. Cleanest legally — makes the lineage explicit.
B. Fresh MIT, same authors, year 2026 "Copyright (c) 2026 Xuefeng Liu, Yuuka Yanagisawa" — separate notice for the Julia port You consider the Julia code a new work (not a strict derivative), so a 2026 notice is more accurate. Both files end up under MIT either way.
C. Dual-list both One LICENSE with both notices (2025 MATLAB + 2026 Julia), explicitly "MIT, derived from veigs/" Maximum provenance clarity. Slightly verbose. Safe if you ever upstream changes back to the MATLAB version.
Recommendation: Option B. The Julia port is genuinely new code — new bugs, new test infrastructure, a different design surface (verified_ldl, error hierarchy, etc.) — even though it's a faithful algorithmic port. A 2026 notice on the Julia tree, keeping the MIT terms, accurately reflects this. If you later want extra-explicit lineage, add a one-line "Derived from the MATLAB veigs toolbox (MIT, 2025)." to the README — lighter than a dual-licensed LICENSE file.

Q-001 — Register on JuliaRegistries?

The Julia General registry is the public Julia package registry. Once a package is registered there, anyone can run Pkg.add("Veigs") and get it via the version resolver. Registration is one-way easy, multi-way hard: you cannot truly unregister a name once published — you can only stop releasing new versions.

Part 1 — Is the package ready for General today?

Not quite. Three blockers:

  1. No public GitHub URL. The package is in a Dropbox folder, not in a git repo. Registration requires a public Git URL.
  2. No CI. The General-registry policy doesn't strictly require CI, but unmaintained packages without it get flagged in practice. Iter 8's .github/workflows/ci.yml should land first.
  3. Package version is 0.1.0-dev. The registry rejects -dev suffixes — you'd bump to 0.1.0 for a real release.

Part 2 — Even when ready, should you publish?

ProCon
Citation: a registered package can get a DOI via Zenodo; useful for academic papers. The name Veigs.jl on General is permanent — can't change later.
Discoverability: JuliaHub, search engines, recommendation lists. Maintenance commitment: bug reports, version bumps for compat, deprecation churn from IntervalArithmetic.jl, etc.
Easier collaboration: anyone can Pkg.add and reproduce results. If the package is tied to one paper's reproducibility, you may want it pinned, not iterating.

Part 3 — Lower-stakes alternatives

You don't need General-registry publication to get most of the benefits. Three lower-stakes paths:

  1. Public GitHub repo, no registration. Users do Pkg.add(url="https://github.com/.../Veigs.jl"). They can pin to a specific commit. Zero ongoing obligation; still cite-able via the GitHub URL or a Zenodo DOI.
  2. Private (or personal) Julia registry. A YAML file you publish on GitHub that declares Veigs.jl. Users add your registry first, then Pkg.add("Veigs"). Useful inside a research group.
  3. Stay path-only. Users Pkg.develop(path="…"). Best for closed collaboration only.
Recommendation, in order:
  1. Now (before iter 8): initialize git, add LICENSE (Option B), push to a private GitHub repo. Costs nothing, fixes Q-002, makes future Q-001 easy.
  2. At iter 8: land CI yaml, bump to 0.1.0, make the GitHub repo public if you're comfortable. Most users can already use the package via Pkg.add(url=...) at this point — you don't yet need the General registry.
  3. Only after a paper or talk references the package: register on General. By then you have a stable v0.1, real users, and a clear reason. Until then, public-but-unregistered is the best risk/reward trade-off.
